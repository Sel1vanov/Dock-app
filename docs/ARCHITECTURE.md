# Архитектура Dock (кейс 5)

```
┌──────────────── Мобильное приложение (src/) ────────────────┐      ┌──────────────────── Сервер API (server/src/) ─────────────────────┐
│ View ─▶ ViewModel ─▶ Service ─▶ Repository ─▶ core/api.ts   │ HTTP │ routers ─▶ services ─▶ repositories ─▶ ORM (models) ─▶ PostgreSQL │
│ экраны   состояние,   сценарии   HTTP-запросы  fetch + JWT   │ JSON │  HTTP     бизнес-      доступ к       сущности     миграции    │
│          проверка форм                                       │      │  схемы    правила,     данным                                      │
└──────────────────────────────────────────────────────────────┘      │           права                                                   │
                                                                       └───────────────────────────────────────────────────────────────────┘
```

## Слои сервера

| Слой | Папка | Отвечает за | Не делает |
|---|---|---|---|
| **routers** | `server/src/routers` | HTTP: путь, метод, схемы запроса/ответа, коды 201/204, документация Swagger | не обращается к БД, не содержит правил |
| **services** | `server/src/services` | бизнес-правила (статусная модель заказа, кто что может), проверка прав и владельца, транзакции, сборка ответа | не знает про HTTP (кроме классов ошибок) |
| **repositories** | `server/src/repositories` | все запросы к БД через ORM: фильтры, сортировка, пагинация, загрузка связей | не принимает решений |
| **models** | `server/src/models` | ORM-модели (таблицы, связи, ограничения) | — |
| **schemas** | `server/src/schemas` | схемы API (zod ≈ Pydantic): типы, обязательность, допустимые значения | — |
| **database** | `server/src/database` | подключение ORM, миграции, CLI миграций, seed | — |
| core | `server/src/core` | конфигурация из окружения, безопасность (bcrypt, JWT, подписи ссылок), классы ошибок, обработчик ошибок | — |
| dependencies | `server/src/dependencies.ts` | «зависимости» обработчиков: Session на запрос, текущий пользователь, проверка роли, сборка сервисов | — |

Пример пути запроса `PATCH /api/v1/orders/{id}`:

1. `dependencies.ts` → `onRequest`: создаётся Session (`orm.em.fork()`), `authenticate` проверяет JWT и загружает
   пользователя (401/403).
2. Fastify проверяет `params` и `body` схемами `IdParams`, `OrderUpdateRequest` (422).
3. `routers/orders.ts` → `services(request).orders.update(user, id, body)`.
4. `services/OrderService.ts`: заявка существует (404), принадлежит пользователю (403), на неё нет откликов (409);
   изменения применяются к сущности, `em.flush()`.
5. `repositories/OrderRepository.ts` загружает карточку со связями, `services/mappers.ts` собирает ответ.
6. Ответ проверяется схемой `OrderDetailsResponse` и уходит клиенту (200).

### Session через механизм зависимостей

```ts
// server/src/dependencies.ts
app.addHook('onRequest', async (request) => { request.em = deps.orm.em.fork(); });  // Session на запрос
export function getSession(request) { return request.em; }                             // ≈ Depends(get_db)
export async function authenticate(request) { … }                                      // ≈ Depends(get_current_user)
export function requireRole(...roles) { … }                                            // проверка роли
export function services(request) { const ctx = { em: getSession(request), config, storage }; … }
```

### Конфигурация

Все параметры — из переменных окружения (`server/.env`, образец `server/.env.example`), разбираются и проверяются
в одном месте — `server/src/core/config.ts` (при неверной конфигурации сервер не стартует и пишет, что не так).
Бизнес-логика к `process.env` не обращается.

### Исключения и журналирование

- Сервисы бросают `NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`, `UnauthorizedError`
  (`core/errors.ts`).
- `core/errorHandler.ts` превращает их, ошибки схем и нарушения ограничений БД в ответы с кодами
  401/403/404/409/422; непредвиденные ошибки — в 500 без подробностей.
- Журнал — pino (встроен в Fastify): каждый запрос (метод, путь, код, время), предупреждения 401/403,
  ошибки 5xx со стеком. Токены и пароли в журнале скрыты (`redact`).

## Слои клиента (MVVM, SAD 5.2)

| Слой | Папка | Что делает |
|---|---|---|
| Маршруты | `src/app` | Expo Router: файл = экран, без логики |
| View | `src/views/screens`, `src/views/components` | отображение, передача действий во ViewModel |
| ViewModel | `src/viewmodels` | состояние экрана, проверка форм до запроса, загрузка/ошибка/успех |
| Service | `src/services` | сценарии UC, предварительные проверки доменных правил |
| Repository | `src/repositories` | вызовы API v1 (по одному на ресурс) |
| Models | `src/models` | DTO для экранов, типы ответов API, мапперы, схемы форм, доменные правила |
| Core | `src/core` | HTTP-клиент с JWT и обработкой 401, хранение токена (SecureStore), адрес сервера, ссылки для звонка и мессенджеров |

Внешний вид задают общие токены `src/views/theme.ts` (цвета, отступы, скругления, шрифт Onest) и компоненты
`src/views/components`: шапка экрана с колокольчиком уведомлений (`ScreenHeader`), нижняя навигация
(`TabBar`), кнопки, карточки, поля ввода.

## Тесты

`npm run test:server` (из корня) или `npm test` (в `server/`). Каждый файл начинает с пустой схемы в отдельной БД
`dock_test`, разворачивает её миграциями и шлёт запросы в приложение через `app.inject()`.

| Файл | Что проверяет |
|---|---|
| `01-database.test.ts` | миграции на пустой БД, совпадение схемы с моделями, откат и повторное применение, CHECK/UNIQUE/FK |
| `02-auth.test.ts` | регистрация (201), дубликат (409), валидация (422), вход/неверный пароль (401), bcrypt-хеш, поддельный и истёкший токен (401), блокировка (403), безопасные ошибки |
| `03-orders-crud.test.ts` | **создание, получение, изменение, удаление** заявки с проверкой строки в PostgreSQL и повторным запросом; ошибочные сценарии 422/403/404; поиск, фильтры, сортировка, пагинация, SQL-инъекция в поиске |
| `04-vehicles.test.ts` | CRUD ТС, связь N:M в промежуточной таблице, каскадное удаление, чужое ТС (403) |
| `05-bids-transactions.test.ts` | отклики (403/409), выбор исполнителя одной транзакцией (begin…commit), **rollback** при сбое — вместе с уведомлениями |
| `06-trip-workflow.test.ts` | интеграционный путь: заявка → отклик → выбор → оплата → этапы рейса с фото → приёмка → отзывы; подписанные ссылки на файлы; отзывы обо мне; уведомления обеим сторонам о каждом этапе |
| `07-n-plus-one.test.ts` | число SQL-запросов не растёт с числом заявок и откликов |
| `08-admin-profile.test.ts` | верификация документов, модерация (403 не админу), профиль, запрет повышения роли |
| `09-bargaining-notifications.test.ts` | встречная цена заказчика и согласие водителя (403/409), уведомления (счётчик, прочтение, чужое — 403), уведомления о проверке документов; смена пароля (422, отзыв старого токена); «Забыли пароль?» → временный пароль от администратора |

Итого 39 тестов. Интеграцию клиента с API дополнительно проверяли вручную в браузере: вход, поиск, создание,
изменение, удаление, выход, лента водителя, отклик, модерация, оплата, фотофиксация, истечение токена;
после добавления уведомлений и встречной цены — колокольчик со счётчиком, экран уведомлений, согласие водителя
на встречную цену, кнопки связи на экране рейса.
