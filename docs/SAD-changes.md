# Изменения относительно SAD и Vision (версия 4.0)

Документы заполнялись вручную и местами расходятся между собой и с кодом. Ниже — что изменено в реализации
и что предлагается перенести в SAD (`docs/Dock_SAD_Selivanov_3.docx`).

## 1. Архитектура: свой сервер API вместо BaaS (SAD, разделы 2–3)

**Было (SAD 3.0):** клиент напрямую обращается к Supabase (PostgREST, Supabase Auth, Storage), бизнес-правила —
в триггерах и RLS-политиках, «без разработки кастомного бэкенда».

**Стало:** клиент работает только с собственным REST API **Dock API v1** (Node.js + TypeScript, Fastify,
MikroORM, PostgreSQL). Причины:

- финальные кейсы требуют версионированного API со схемами, Swagger и кодами ответов, ORM с транзакциями,
  слоистой архитектуры сервера с тестами и собственной реализации регистрации/хеширования/JWT;
- правила (статусная модель, права, проверка владельца) теперь в одном месте — сервисном слое, на TypeScript,
  и покрыты тестами, а не разнесены по триггерам и политикам;
- клиент не зависит от SDK конкретного облака; Supabase не используется совсем — база PostgreSQL разворачивается в Docker.

Что предлагается заменить в SAD:

| Раздел SAD | Новая формулировка |
|---|---|
| 2. Ограничения | «Клиент-серверная архитектура: мобильное приложение ↔ REST API ↔ PostgreSQL. Единый язык TypeScript на клиенте и сервере» |
| 2. Инструменты | + Node.js 22, Fastify 5, MikroORM 7, zod, bcrypt, JWT; `@supabase/supabase-js` больше не используется |
| 3. Архитектурное представление | Авторизация — собственная (bcrypt + JWT), хранение файлов — сервер API с подписанными ссылками |
| 5.1. Слои | Клиент: View → ViewModel → Service → Repository → HTTP. Сервер: routers → services → repositories → ORM → PostgreSQL — см. [ARCHITECTURE.md](ARCHITECTURE.md) |
| 5.2. Пакеты | + пакеты Services, DTO; репозитории клиента — HTTP-клиенты API; на сервере — пакеты routers, services, repositories, models, schemas, database |
| 7. Развёртывание | Мобильные устройства (iOS/Android, Expo) и браузер → HTTPS → сервер Dock API (Node.js) → PostgreSQL 17 (контейнер Docker, `docker-compose.yml`) |
| 8. Реализация | структура репозитория из [README.md](../README.md) |
| 9. Данные | ER-диаграмма и ограничения — [DATABASE.md](DATABASE.md); эндпоинты версии 4.0 — [API.md](API.md) |

## 2. Эндпоинты (SAD, раздел 9) — версия 4.0

Таблицы эндпоинтов версий 2.0 и 3.0 описывали PostgREST Supabase (`/rest/v1/…`). Они заменяются API v1:
46 эндпоинтов под `/api/v1`, полная таблица — в [API.md](API.md), интерактивно — Swagger `/docs`.
Ответы `DELETE` теперь `204 No Content` (а не `{"success": true}`), строка выбирается по id в пути
(`PATCH /orders/{id}`), выбор исполнителя — `POST /bids/{id}/accept` (одна транзакция).

## 3. Статусная модель заказа (SAD 5, класс Order)

В SAD у `Order.status` три значения (`Created, InProgress, Completed`), в Vision этапов больше. В реализации:

| Статус | Как назван в Vision | Кто переводит | Условие |
|---|---|---|---|
| `Created` | Поиск исполнителя | — | заявка опубликована; можно изменить и удалить |
| `Bidding` | (идёт торг) | автоматически | первый отклик; если все отклики отозваны — снова `Created` |
| `Assigned` | Ожидает оплаты | заказчик (выбор отклика) | |
| `Assigned` + оплачен | Оплачен / ожидает погрузки | заказчик | безопасная сделка (демо) |
| `Loading` | Прибыл на погрузку | водитель | только после оплаты |
| `InTransit` | В пути | водитель | есть фото погрузки |
| `Unloading` | Прибыл на выгрузку | водитель | — |
| `Completed` | Завершён | заказчик (приёмка) | есть фото выгрузки; средства переводятся |
| `Cancelled` | Отменена | заказчик | до оплаты, с причиной |

Статус `Disputed` и таблица `disputes` удалены: споры (UC-20, UC-21) не реализованы и перенесены на следующий
этап — в схеме не держим неиспользуемых таблиц.

## 4. Изменения модели данных

| Было | Стало | Зачем |
|---|---|---|
| `users.is_verified` (bool), `verification_doc_url` | `verification_status` (`none/pending/verified/rejected`), `verified_at`, `verified_by_id` + таблица `verification_documents` | у проверки 4 состояния, документов 3 вида, нужен автор решения (миграция 2) |
| пароли в Supabase Auth | `users.password_hash` (bcrypt) | собственная авторизация |
| `orders.cargo_type` (enum) | справочник `cargo_types` + FK | тип груза — справочные данные |
| — | `vehicle_cargo_types` (N:M) | лента учитывает, какие грузы возит ТС (эвакуатор не видит экскаваторы) |
| `photo_url` с публичной ссылкой | `file_key` + временная подписанная ссылка | фото и документы не публичны |
| `origin_lat/lng`, `special_permits_url` | удалены | карта и спецразрешения — следующий этап |
| enum-типы PostgreSQL | `text` + CHECK | проще менять миграциями |
| — | `bids.counter_price` | встречная цена заказчика — двусторонний торг (миграция 3) |
| — | таблица `notifications` | уведомления о событиях заявки, торга, рейса и модерации (миграция 3) |
| — | `users.password_changed_at` | смена пароля завершает прежние сессии (миграция 3) |

Единицы: в БД и API — килограммы и метры, в интерфейсе — тонны и метры (конвертация в мапперах DTO).

## 5. Несоответствия в Vision

- UC-12, шаг «Заморозить средства (UC-15)» → должно быть **UC-13**.
- UC-18, предусловие ссылается на UC-19 → должно быть **UC-15/UC-17** (статус «Прибыл на выгрузку» и фото).
- Раздел 6 «Целевые платформы: iOS» расходится с SAD (iOS/Android). React Native даёт обе — указать iOS и Android.
- Раздел 6 «Доступ к полной ленте — только после проверки»: реализовано мягче — непроверенный водитель видит
  ленту только для просмотра, отклик запрещён (403). Так видно, зачем проходить проверку.
- Торг двусторонний: водитель откликается по цене заказчика или со своей ценой (UC-10, UC-11), заказчик может
  ответить встречной ценой на конкретный отклик, водитель соглашается на неё или меняет свою цену; заказчик
  выбирает исполнителя по согласованной цене.
- Модерация (UC-02, UC-22) в SAD отнесена к веб-панели администратора; пока она встроена в мобильное приложение
  (роль Admin видит вкладку «Модерация»), API для веб-панели уже есть (`/api/v1/admin/…`). Там же администратор
  выдаёт временный пароль по просьбе «Забыли пароль?».

## 6. Возможности, которых нет в SAD и Vision

| Возможность | Как сделано |
|---|---|
| Уведомления | Сервер создаёт уведомление в той же транзакции, что и событие; в приложении — колокольчик со счётчиком непрочитанных (опрос раз в 30 секунд, пока приложение открыто) и экран уведомлений с переходом к заявке или рейсу. Push-уведомлений на телефон нет |
| Связь с контрагентом | Встроенного чата нет. После выбора исполнителя стороны видят телефоны друг друга; кнопки «Позвонить», WhatsApp и Telegram открывают соответствующие приложения |
| Смена и сброс пароля | Смена пароля в профиле; «Забыли пароль?» — просьба администратору, который выдаёт временный пароль ([SECURITY.md](SECURITY.md)) |
| Автообновление | Открытые карточка заявки и экран рейса перечитываются каждые 15 секунд — отклики, встречная цена и этапы рейса появляются без обновления вручную |
