# 1. Что это за проект (скажи своими словами)

**Dock** — мобильное приложение для перевозки негабаритных грузов.

- Заказчик публикует заявку: габариты, вес, тип груза, маршрут, цена.
- Водитель с подходящей техникой откликается. Можно торговаться: у водителя своя цена, у заказчика встречная.
- Заказчик выбирает исполнителя и «оплачивает». Деньги замораживаются (escrow, «безопасная сделка»).
- Водитель проходит рейс: погрузка → в пути → выгрузка. На погрузке и выгрузке **обязательно фото**.
- Заказчик подтверждает приёмку, и сделка завершена.
- Если что-то пошло не так, любая сторона открывает **спор**, и решает администратор.

**Три роли:**

- **Client** — заказчик.
- **Driver** — водитель.
- **Admin** — администратор: проверяет документы водителей, блокирует пользователей, решает споры.

# 2. Архитектура в целом

```
Телефон / браузер ──HTTP + JWT──▶ Сервер (Fastify) ──ORM──▶ PostgreSQL (Docker)
 Expo + React Native              порт 8000, /api/v1          порт 5432
 папка src/                       папка server/src/
```

- **Клиент** (`src/`): React Native + Expo Router, архитектура **MVVM**.
- **Сервер** (`server/src/`): Fastify + MikroORM (превращает таблицы в TypeScript-классы) + zod (проверка данных) + JWT (токены).
- **База**: PostgreSQL 17 в Docker. Схема создаётся **миграциями**.
- **Запуск**: `npm run dev` запускает `scripts/dev.mjs`. Он поднимает базу, применяет миграции, заливает демо-данные, запускает сервер и Expo.
- **Документация API**: Swagger на `localhost:8000/docs`. Покажи её на защите.

## Ответ на «как всё связано» (30 секунд, выучи)

> «Приложение состоит из трёх частей: мобильный клиент, сервер и база. Клиент общается с сервером по HTTP, передавая JWT-токен. Сервер разбит на слои: роутер принимает запрос и проверяет формат, сервис применяет правила бизнеса и права, репозиторий ходит в базу через ORM, модели описывают таблицы. Клиент устроен так же по слоям, по MVVM: экран, вьюмодель, сервис, репозиторий, HTTP-клиент. Слои зависят только от соседа ниже и никогда наоборот».

## Главное правило

**Зависимости идут только сверху вниз.** Экран знает вьюмодель, вьюмодель не знает экран. Репозиторий не знает про бизнес-правила. Модель не знает про HTTP. Поэтому любой слой можно заменить, не трогая остальные.

# 3. Путь одного запроса (самое важное)

Пример: **водитель откликается на заявку**. Это запрос `POST /api/v1/orders/{id}/bids`.

## На телефоне (клиент)

1. **View** `views/screens/OrderDetailsScreen.tsx`. Кнопка «Откликнуться». Только рисует.
2. **ViewModel** `viewmodels/OrderDetailsViewModels.ts`. Состояние экрана (поле цены, ошибки), проверка формы по `bidSchema`.
3. **Service** `services/BidService.ts`. Предпроверки, чтобы сразу показать понятную ошибку: водитель верифицирован, заявка открыта, техника подходит.
4. **Repository** `repositories/BidRepository.ts`. Одна строка: `apiRequest('POST', '/orders/${id}/bids', ...)`.
5. **core/api.ts**. Добавляет `Authorization: Bearer <токен>`, ставит таймаут 20 секунд, разбирает ошибки. На ответ 401 разлогинивает. Тихо продлевает токен на половине его срока.

Цепочка: **View → ViewModel → Service → Repository → api.ts → сервер**.

## На сервере

1. **`app.ts`**. Принимает запрос. До маршрутов работают CORS, rate limit и валидация.
2. **`dependencies.ts`**. На каждый запрос создаётся свой `EntityManager` (`orm.em.fork()`). Хук `authenticate` проверяет JWT, находит пользователя, проверяет блокировку и версию пароля.
3. **Router** `routers/orders.ts`. Описывает маршрут и схему zod. Если тело неверное, сразу 422. Обработчик в одну строку вызывает метод сервиса.
4. **Service** `services/BidService.ts` — **здесь правила бизнеса**. Проверяет роль, верификацию, статус заявки, дубль отклика, `fitsVehicle` (влезает ли груз в ТС). Создаёт отклик, переводит заявку `Created → Bidding`, создаёт уведомление заказчику.
5. **Repository** `repositories/BidRepository.ts`. Запросы к базе.
6. **Model** `models/Bid.ts`. Класс, соответствующий таблице.
7. **`em.flush()`**. Все изменения (отклик, статус заявки, уведомление) уходят **одной транзакцией**.

Слои сервера: **Router → Service → Repository → Model**.

Ответ идёт обратно тем же путём: сервер возвращает актуальную карточку заказа (`OrderService.getDetails`), клиент превращает её через mapper в DTO, и экран обновляется.

## Что делает «Выбрать исполнителя» (`BidService.accept`)

Это одна транзакция с явными `begin / commit / rollback`:

1. Начинается транзакция (`em.begin()`).
2. Заявка **блокируется** (`SELECT ... FOR UPDATE`). Если два запроса придут одновременно, второй подождёт.
3. Проверяется, что выбирает автор заявки, что заявка ещё открыта, что отклик ожидает решения.
4. В заказ записываются водитель и цена, статус становится `Assigned`, отклик становится `Accepted`.
5. Выбранному водителю уходит уведомление «Вас выбрали». Остальным — «Выбран другой исполнитель», их отклики отклоняются.
6. `commit`. Если любой шаг упал — `rollback`, в базе не остаётся половины изменений.

# 4. Жизнь заказа (статусы)

Определены в `models/enums.ts`. Переходы защищены правилами в сервисах.

```
Created ──(первый отклик)──▶ Bidding ──(заказчик выбрал водителя)──▶ Assigned
Assigned ──(заказчик платит: isEscrowLocked = true)
Assigned ──▶ Loading ──▶ InTransit ──▶ Unloading     (водитель, TrackingService)
Unloading ──(заказчик подтверждает приёмку)──▶ Completed
```

Дополнительно:

- **Cancelled**. Отмена возможна, пока заявка открыта, или после выбора водителя, но **до оплаты**.
- **Disputed**. Спор можно открыть, пока рейс идёт и деньги заморожены. Рейс встаёт на паузу.
  - Админ решает «в пользу заказчика»: заказ `Cancelled`, деньги возвращаются.
  - Админ решает «в пользу водителя»: заказ `Completed`, деньги уходят водителю.

## Защита от нарушения порядка (`TrackingService`)

- Начать погрузку можно **только после оплаты**.
- Перейти в «в пути» можно **только после фото погрузки**.
- Статусы идут только вперёд (карта `DRIVER_TRANSITIONS`). Перескочить нельзя.
- Фото погрузки грузится только на статусе «прибыл на погрузку», фото выгрузки — на «прибыл на выгрузку».

## Совпадение груза и техники (`fitsVehicle`)

Вес, длина, ширина и высота груза не больше возможностей ТС, и ТС возит такой тип груза. Водитель видит в ленте только подходящие заявки.

## Честно про оплату

Реального платёжного шлюза в проекте нет. `pay()` ставит флаг `isEscrowLocked = true`, а при завершении или споре снимает его. Это **эмуляция** безопасной сделки. Если спросят, скажи прямо: это учебная модель, интеграция с платёжной системой не входит в проект.

# 5. Безопасность

- **Пароли**: bcrypt, 12 раундов (около 250 мс на хеш). Есть «хеш-пустышка», чтобы по времени ответа нельзя было понять, существует ли email.
- **JWT**: подпись HS256, проверяются issuer, audience и срок. Внутри: id пользователя, роль, версия пароля (`pwv`), время входа (`sst`).
  - Сменил пароль → старые токены перестают работать.
  - Продление сессии не бесконечное: максимум 30 дней (`SESSION_MAX_AGE`).
- **Роли**: `requireRole(...)` и проверки владельца в сервисах (например, «выбрать исполнителя может только автор заявки»).
- **Приватные файлы** (паспорт, фото): подписанные временные ссылки (HMAC, срок 1 час). Без подписи ссылка не работает. Аналог signed URL в S3.
- **Ошибки**: сервисы кидают `ConflictError`, `ForbiddenError` и т.п. с понятным текстом. Обработчик превращает их в `{error: {code, message}}`. Стек и SQL наружу не уходят.
- **Логи**: пароли и токены вырезаются из логов.
- **Секреты** лежат в `server/.env`, в git их нет.
- **Запрещённые имена**: нельзя назваться «Администратор» или «Поддержка Dock» (`reservedNames.ts`), чтобы не выдать себя за сотрудника. Учитываются обходы: цифры вместо букв, русские буквы вместо латинских.

## Коды ответов

| Код | Значение |
|---|---|
| 401 | Не вошёл или токен протух |
| 403 | Вошёл, но нет прав |
| 404 | Не найдено |
| 409 | Конфликт: неверный статус, дубль |
| 422 | Неверные данные |

# 6. База данных

- **Миграции** (`database/migrations/`) создают схему шагами. Названия с датой показывают порядок: начальная схема, верификация и поиск, уведомления и торг, формат телефона, споры, уникальный телефон.
- **Таблицы**: users, vehicles, cargo_types, orders, bids, order_photos, reviews, notifications, disputes, verification_documents.
- **CHECK-ограничения в самой базе** (смотри `models/Order.ts`):
  - у `Created` и `Bidding` водителя нет, у `Assigned` и дальше он есть;
  - нельзя быть в `InTransit` без замороженной оплаты;
  - цена и габариты больше нуля.
  - Следствие: даже при ошибке в коде база не примет неправильную комбинацию.
- **Индексы**: по клиенту и дате, по водителю, **частичный** индекс по открытым заявкам, триграммный GIN-индекс для текстового поиска.
- **Транзакции**: обычно хватает `em.flush()` (всё одной транзакцией). Явные `begin/commit/rollback` и `FOR UPDATE` — в `BidService.accept` и `DisputeService.resolve`.
- **Защита от дублей**: уникальный индекс. Если оба участника открыли спор одновременно, второго отсечёт частичный уникальный индекс, сервер вернёт 409.
- **N+1** (на список из N записей делается N+1 запросов) решён через `loadStrategy: 'balanced'` и пакетные запросы. `DB_DEBUG=true` печатает SQL, это можно показать.
- **Поиск**: значение идёт параметром, спецсимволы `%` и `_` экранируются (`repositories/query.ts`).

# 7. Клиент подробнее

- **Маршруты**: `src/app/`. Файл = экран. `order/[id].tsx` — динамический маршрут: берёт `id` из адреса и отдаёт экрану.
- **`app/_layout.tsx`**: корень. Оборачивает всё в `AuthProvider` и `NotificationsProvider`. **`Stack.Protected`** показывает экран входа, если пользователь не вошёл, и остальные экраны, если вошёл.
- **Вкладки** `(tabs)/`: лента, мои заказы, мои рейсы, создание, модерация, профиль. Какие вкладки видны, зависит от роли.
- **ViewModel**: хуки состояния. `useQuery` загружает данные, `useAction` выполняет действие. Карточка заказа каждые 15 секунд перечитывается сама, поэтому новые отклики появляются без ручного обновления.
- **`models/domain.ts`**: чистые правила (`canPay`, `canCancel`, `checkCompatibility`). По ним решается, какие кнопки показывать.
- **`models/schemas.ts`**: zod-схемы форм.
- **api → dto → mappers**: `api.ts` — что приходит с сервера (килограммы), `dto.ts` — что нужно экрану (тонны), `mappers.ts` — превращает одно в другое. Поменялся формат API — правится только маппер.
- **Токен**: `core/tokenStorage.ts`. На телефоне — защищённое хранилище ОС, в вебе — localStorage.

**Мысль для защиты:** проверки есть и на клиенте, и на сервере. Клиентские нужны для удобства (быстрое сообщение). Сервер проверяет **окончательно**, потому что клиенту доверять нельзя.

# 8. Карта папок

## Корень

| Что | Роль |
|---|---|
| `package.json` | Главный пульт со скриптами `dev`, `server`, `db:reset`. `postinstall` ставит зависимости сервера и создаёт `server/.env` |
| `scripts/dev.mjs` | Команда `npm run dev`: Postgres в Docker → миграции и seed → сервер в фоне → Expo. Ctrl+C гасит всё |
| `docker-compose.yml` | Контейнер PostgreSQL 17 (логин, пароль, база `dock`) |
| `app.json` | Паспорт мобильного приложения: имя, иконка, ориентация |
| `tsconfig.json`, `eslint.config.js` | Проверка типов и стиля |
| `assets/` | Иконки |
| `.env.example` | Образец необязательной настройки адреса сервера |

## Сервер `server/src/`

- **`main.ts`**. Запуск: конфиг → ORM → проверка миграций → `listen`.
- **`app.ts`**. Сборка Fastify: CORS, rate limit, Swagger, обработчик ошибок, маршруты. Вынесен отдельно, чтобы тесты поднимали то же приложение.
- **`dependencies.ts`**. Склейка запроса: EntityManager на запрос, `authenticate`, `requireRole`, `services(request)`.
- **`core/`**. Общий фундамент: `config`, `security`, `errors`, `errorHandler`, `reservedNames`. Им пользуются все слои, а сам он ни от кого не зависит.
- **`routers/`**. Слой HTTP. Файл на группу маршрутов (`auth`, `users`, `vehicles`, `orders`, `bids`, `admin`, `notifications`, `catalog`, `files`). Принимает запрос, проверяет схему, вызывает **один** метод сервиса. Бизнес-логики нет.
- **`schemas/`**. Контракт API на zod. По ним Fastify проверяет данные, и по ним же строится Swagger. С ORM-моделями не связаны, поэтому `password_hash` в ответ попасть не может.
- **`services/`**. Сердце проекта, бизнес-логика:
  - `AuthService` — регистрация, вход, продление токена, смена пароля;
  - `UserService` — профиль, документы водителя;
  - `VehicleService` — техника и типы грузов;
  - `OrderService` — заявки, лента, оплата, приёмка, отмена;
  - `BidService` — торг и выбор исполнителя;
  - `TrackingService` — статусы рейса и фото;
  - `DisputeService` — споры;
  - `ReviewService` — отзывы;
  - `AdminService` — верификация и блокировка;
  - `NotificationService` — уведомления (его вызывают остальные);
  - `FileStorage` — хранение файлов (через интерфейс, можно заменить на S3);
  - `mappers.ts` — решает, какие поля уходят клиенту.
- **`repositories/`**. Доступ к данным: по репозиторию на таблицу. Только запросы к базе. Вызываются только из сервисов.
- **`models/`**. Таблицы как классы (`User`, `Order`, `Bid`...) со связями, индексами и CHECK. `enums.ts` — все перечисления и группы статусов.
- **`database/`**. `orm.ts` — подключение; `migrate.ts` — запуск миграций (`up`, `down`, `status`); `migrations/` — SQL-миграции; `seed.ts` — демо-данные; `seed-assets/` — картинки для демо.
- **`server/scripts/init-env.mjs`**. Создаёт `server/.env` со случайными секретами.

## Клиент `src/`

- **`app/`**. Карта экранов (Expo Router). Тонкие обёртки: берут параметры адреса и отдают экрану.
- **`views/`**. Только внешний вид. `screens/` — экраны, `components/` — кнопки, карточки, `TabBar`, `ToastHost`, `theme.ts` — цвета, шрифты, отступы.
- **`viewmodels/`**. Состояние и поведение экрана. `AuthViewModel` — кто вошёл. `useAsync.ts` — общие хуки `useQuery` и `useAction`.
- **`services/`**. Сценарии: предпроверки и превращение ответа в DTO.
- **`repositories/`**. HTTP-запросы, по одной строке на метод. Единственное место, где написаны адреса эндпоинтов.
- **`models/`**. `api.ts`, `dto.ts`, `mappers.ts`, `domain.ts`, `schemas.ts`, `catalog.ts`.
- **`core/`**. `api.ts` (HTTP-клиент), `config.ts` (адрес сервера), `tokenStorage.ts`, `errors.ts`, `platform.ts` (диалоги, камера), `toast.ts`, `phone.ts`, `contacts.ts`.

## Связь в двух предложениях

**По вертикали:** экран → вьюмодель → сервис → репозиторий → `api.ts` → HTTP → роутер → сервис → репозиторий → модель → PostgreSQL.
**По горизонтали:** `core/` и `models/` — общие справочники, которыми пользуются все слои, но сами они от верхних слоёв не зависят.

# 9. Запуск сервера, строка за строкой (`server/src/main.ts`)

| Строка | Что отвечать |
|---|---|
| `loadEnvFile()` | Читает `server/.env` в `process.env`. Секреты не лежат в коде и git |
| `loadConfig()` | Проверяет переменные через zod и возвращает типизированный `Config`. Неверная настройка — сервер сразу падает с понятным текстом |
| `await initOrm(config)` | Подключается к PostgreSQL через MikroORM |
| `orm.migrator.getPending()` | Список непримененных миграций. Если не пустой — только предупреждение, сервер не падает |
| `buildApp({ config, orm })` | Создаёт Fastify со всеми маршрутами. Конфиг и ORM передаются снаружи (dependency injection) |
| `process.on('SIGINT', shutdown)` | При Ctrl+C сначала закрывает HTTP, потом базу, потом процесс |
| `app.listen({ host, port })` | Запускает сервер. `0.0.0.0` нужен, чтобы телефон в той же Wi-Fi сети мог достучаться |
| `import ... from './app.js'` | Расширение `.js`, потому что проект на ES-модулях. Файл на самом деле `app.ts` |

Цепочка: **env → конфиг → база → проверка миграций → приложение → слушаем порт**.

# 10. Короткие справки

## Настройки `.env`: что и зачем

| Файл | Чья настройка | В git? |
|---|---|---|
| `.env.example` (корень) | Клиент. Одна строка: `EXPO_PUBLIC_API_URL` | Да |
| `server/.env.example` | Образец настроек сервера с заглушками | Да |
| `server/.env` | Рабочие настройки сервера с настоящими секретами | **Нет** |

- `server/.env` создаётся автоматически при `npm install` скриптом `init-env.mjs`: копирует образец и подставляет случайные `JWT_SECRET` и `FILE_URL_SECRET`.
- **Корневой `.env` нигде не создаётся автоматически и для демо не нужен.** Клиент сам определяет адрес сервера (`src/core/config.ts`). Файл нужен, только если сервер запущен на другом компьютере.
- Префикс `EXPO_PUBLIC_` обязателен: такие переменные попадают в код приложения на телефоне, они публичны. Секретам там не место.

## CORS

**CORS** — правило **браузера**. Страница с одного origin (протокол + хост + порт) не может обращаться к API на другом origin, пока сервер не разрешит. Веб-версия открывается на `localhost:8081`, API на `localhost:8000`, поэтому нужен CORS. В `app.ts` он настраивается через `CORS_ORIGIN`: `*` — разрешить всем (только для разработки), в продакшене указывают конкретные адреса. Мобильное приложение CORS не затрагивает. CORS — не защита сервера, защиту даёт JWT. `OPTIONS` — предварительный запрос, которым браузер спрашивает разрешение.

## Миграции

- Это версионирование схемы базы: каждое изменение — отдельный файл с методами `up()` (применить) и `down()` (откатить).
- Применённые записываются в таблицу `mikro_orm_migrations`, поэтому применяются только новые.
- В проекте они написаны вручную на SQL. Только первую сгенерировали по моделям ORM и доработали. Автогенерация не умеет сложное: проверку данных перед ограничением, частичные индексы, триграммный GIN, CHECK по комбинации статусов.
- Список миграций в `migrations/index.ts` **явный**: новый файл надо добавить туда вручную.
- Команды: `db:migrate`, `db:migrate:down`, `db:status`.

## `override`

Ключевое слово TypeScript: «этот метод переопределяет метод родительского класса». В миграциях `override up()` переопределяет метод из класса `Migration` библиотеки MikroORM. Если в родителе нет такого метода (опечатка в названии), TypeScript выдаст ошибку. Само слово работу не меняет, оно нужно для безопасности.

# 11. Вопросы и ответы

| Вопрос | Ответ |
|---|---|
| Как устроена архитектура? | Клиент-сервер. Клиент на React Native по MVVM, сервер на Fastify со слоями router → service → repository → model, база PostgreSQL |
| Зачем слои? | Каждый отвечает за своё. Правила не зависят от HTTP и SQL, их проще менять и тестировать |
| Как работает авторизация? | Логин возвращает JWT. Клиент шлёт его в `Authorization: Bearer`. Хук `authenticate` проверяет подпись, срок, блокировку и версию пароля |
| Где хранятся пароли? | Только bcrypt-хеши, 12 раундов |
| Как разграничены роли? | `requireRole` и проверки в сервисах (владелец заявки, назначенный водитель) |
| Как защищены файлы? | Подписанные временные ссылки (HMAC, 1 час) |
| Что такое миграции? | Версионируемые шаги изменения схемы. Можно применить и откатить |
| Что при одновременном выборе водителя? | `SELECT FOR UPDATE` блокирует заявку. Побеждает одна транзакция, вторая получает 409 |
| Что такое DI в проекте? | Конфиг, ORM и хранилище файлов передаются в `buildApp` и в сервисы через контекст, а не берутся из глобальных переменных |
| Как валидируются данные? | zod на сервере (в роутерах) и на клиенте (`schemas.ts`), плюс CHECK в базе |
| Реальная оплата есть? | Нет, escrow эмулируется флагом `isEscrowLocked` |
| Зачем `.js` в импортах TypeScript? | ES-модули требуют расширения. Файлы `.ts`, импорт как `.js` |
| Почему проверки и на клиенте, и на сервере? | Клиент — для удобства, сервер проверяет окончательно: клиенту доверять нельзя |
| Что такое N+1 и как решено? | Когда на список из N записей делается N+1 запросов. Решено JOIN-загрузкой и пакетными запросами `IN (...)` |
| Что такое CORS? | Правило браузера для запросов между разными origin. Нужно для веб-версии |

## Если спросят «что делает эта строка»

Отвечай по схеме из четырёх вопросов:

1. **Что делает** одной фразой.
2. **Откуда** берёт данные.
3. **Куда** передаёт результат.
4. **Что будет, если убрать.**

Если не знаешь, не выдумывай. Скажи: «Здесь вызывается `X` из файла `Y`, давайте покажу» — и открой этот файл. Преподавателю важно, что ты ориентируешься в проекте.
